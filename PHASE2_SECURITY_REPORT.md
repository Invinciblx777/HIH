# AegisLab Phase 2: adversarial security proof (23 Oct 2026)

Team Tech Mavericks · Hack in Hills '26 · Track 04. Scope: attack the local prototype, repair what breaks, keep the proof. Nothing was deployed, published, pushed or exposed beyond loopback. All payloads and credentials are synthetic. Phase 3 was not started.

Locations (relative to the folder that holds `phase2/`): working copy `phase2/work/`, **candidate release `phase2/candidate/release_2026-10-23_rc2/`** (386 files listed in its own `MANIFEST.sha256`), logs `phase2/logs/`, proof-of-concept `phase2/tools/poc_mailbox_attacks.py`, evidence `phase2/candidate/release_2026-10-23_rc2/aegislab/evidence/phase2_2026-10-23/`. The Phase 1 candidate (`phase1_closeout/candidate/release_2026-10-22_rc1/`) and the shipped release (`release_2026-10-22/`) were not modified; the candidate was not promoted.

## 1. Executive summary

* **The Phase 1 controls did not hold against a hostile tenant.** Thirteen findings: **five HIGH, five MEDIUM, three LOW**. The worst: code inside a tenant sandbox could make the broker overwrite a file outside the mailbox (shown from a real hardened container, where the run's audit log was destroyed), could redirect every broker write into a directory of its choosing by replacing its mailbox directory, and could hang the broker with a FIFO. Separately, an anonymous caller could cause a genuine release to fail verification or corrupt the vault's checkpoint index, by sending denied requests while a reviewer released.
* **All thirteen were repaired at the root cause** (mount layout, descriptor-relative no-follow I/O, a per-run lifecycle lock, checkpoint serialisation, bounded and validated tenant input, a time budget for blue-team regular expressions, verifier key pinning). Each has a regression test; the new tests were run against the unmodified Phase 1 code first and the relevant ones failed there (section 7).
* **The test suite is 297 tests (144 from Phase 1, 153 added), all passing**, stable over repeated runs. The candidate passes manifest, quickstart (8/8), security demo (33/33 plus the documented limit), claims checker (14/14 and 78/78; full mode result in section 11), strict verification of the valid completed bundles, and rejection of truncated and modified evidence.
* **What is still trusted, and now stated with a test:** the broker and its signing key (a compromised broker signs a false but consistent run), the host kernel and runtime, and global per-role tokens. A key thief who replaces every retained copy is detected only by a reviewer who wrote down the terminal hash at release; the new `--expect-terminal-hash` supports that. None of this was solved by adding cryptography.
* **One earlier claim did not reproduce.** The Phase 1 figure "an unrestricted CPU neighbour raises mailbox round trip by +37.5% to +51.7%" was not seen in three smaller Phase 2 executions on a quiet host (-4.9% to +0.6%). Both are recorded; the effect depends on host conditions; no immunity is claimed.
* **Verdict: PASS**, with the limitations in section 10 and the Phase 3 list in section 12.

## 2. Attacker assumptions

Full table with what each attacker is meant to be stopped from, what was executed, and what is trusted away: `aegislab/THREAT_MODEL.md` section 6. In short, the ten attackers are: (1) a malicious red tenant with code in its sandbox; (2) a malicious blue tenant (config author); (3) the model worker; (4) an observer with no or a bad token; (5) an authenticated but wrongly privileged user; (6) a process manipulating files in its permitted writable area; (7) a process causing resource exhaustion or timing interference; (8) a log editor who cannot change independently retained checkpoints; (9) a compromised trusted broker; (10) a signing-key thief who controls every retained copy.

Designed to be resisted: 1-8. Trusted away, not defended: 9 and 10 (10 only reviewer-mitigable), the host kernel, the container runtime and SELinux policy, hardware side channels, and a compromised verifier. The prototype's tenant processes run as the same host user as the control plane (`--userns keep-id`, uid 1000); separation rests on the sandbox, not on Unix users.

## 8. Audit, role, broker, race and monitoring results

* **Audit.** All 16 mutation classes make strict verification exit 1 without a traceback; the valid bundle exits 0; the in-progress mode is reported as `terminal_verified:false` and never as a pass of strict verification; a bundle from another run, a foreign checkpoint in the vault and a foreign anchor are all rejected when the expected run id is given. A bundle rebuilt end to end with an attacker's key verifies when the key comes from the bundle (exit 0, now labelled "NOT pinned") and is rejected once the real key is pinned. A re-signing key thief is rejected only with `--expect-terminal-hash`. A compromised broker's false run verifies (limitation L-01).
* **Trusted broker: what it can do, demonstrated.** `test_P2A20` builds a run whose six `attack.evaluated` entries all say `safe_output` regardless of what happened; it is signed, released, exported and verified (exit 0). Low-risk improvements added: reviewer-side key pinning and terminal-hash pinning, so the reviewer no longer depends on files the attacker can rewrite after release. Not done, deliberately: a second signature by the same machine, a separate signer process, an independent witness of lifecycle transitions. These change the architecture and none helps against a broker compromised before release.
* **Role matrix.** Section 3. `read artifacts` is denied in every state except RELEASED, and in RELEASED only for reviewer, blue and red participants; a FAILED run exposes nothing; evidence is reviewer-only before release.
* **Broker abuse.** After the fix a hostile red tenant can fill, corrupt or remove entries in its own `in/` and `out/` but cannot move those directories, redirect or block a write, fail the run, or grow the signed log beyond 100 denial entries; a mailbox it breaks ends the run as sealed incomplete with one `mailbox.violation` entry.
* **Races.** Section 3; 25 iterations x 6 threads per stress loop; no failure on the Phase 2 code in 3 consecutive full runs.
* **Monitoring.** Payload, model output, defence config, tokens and PEM markers: 0 hits in the monitor stream, audit log, checkpoints, `run.json`, public API bodies and process output (`P2B52`, `P2C33`, matrix). Tenant text in the monitoring stream was found and fixed (P2-11).

## 10. Trusted-broker and shared-host residual risks

* The broker process, its signing key and the files it writes are one trust domain with the control plane; tenant containers run as the same host user. A broker compromise, a container-runtime or kernel escape, or reading `var/keys/` defeats every guarantee, and a verifier cannot detect false entries the broker signed (L-01, L-07).
* The retained copies are independent only when `AEGIS_VAULT` and `AEGIS_ANCHORS` point at storage the run-directory writer cannot reach (L-04). The terminal-hash pin is only as good as the reviewer's note of it (L-02).
* Tokens are global per role and the `runs.*` functions trust their caller (L-03). No rate limit, request-body limit or TLS in front of the API; run it on loopback only.
* The host is shared: caches, memory bandwidth, the scheduler and the host's other processes are outside the isolation. Timing and refusal channels are reduced, not shown removed (Phase 1 figures stand for their conditions).
* Not tested: character and block devices (cannot be created unprivileged), the HTTP layer beyond a loopback smoke test, other hosts, Docker or Kubernetes, host-kernel or runtime escapes (out of scope by instruction), a larger request body than 20 MiB, and the real-model path beyond the existing 31 adapter tests.
