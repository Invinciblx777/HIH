## 4. Timing and resource interference

**Status (Phase 1 closeout).** The first of the three timing executions reported on 22 Oct had **no raw file** and ran on **earlier code**, and the round-trip figures 2.72 ms, 4.62 ms, p99 8.2 ms and +70% had no saved source. Those numbers are **historical and unverified** (table at the end of this section) and are no longer used for any claim about the shipped code. Everything below comes from **three fresh, complete executions** of the shipped code, with run ids, source hashes and every raw observation saved in `aegislab/evidence/closeout_2026-10-22/timing/` (`README.md` there lists the commands and hashes). Recompute the claims with `python evaluation/check_claims.py`; it recomputes accuracy, median and p99 from the raw files and fails if a document quotes a different number.

**Method.** `evaluation/timing_closeout.py` reuses the held-out classifier, statistics and run driver of `evaluation/timing_eval.py` unchanged. Per padding setting: 20 runs × 10 attacks = 200 requests per execution (100 refused, 100 answered; majority baseline 0.50). Classifier: the best single latency threshold, fitted on training runs only and scored on held-out runs (grouped 5-fold by run, so no run is in both); Wilson 95% intervals; permutation test (1000 shuffles of the whole procedure). Padding settings (0, 100, 250, 500 ms) were fixed in advance and not tuned on these data. Runs of the four settings were interleaved in a seeded random order. Seeds 20261022–20261024; fresh state per execution; every run usable, no failures. The latency is measured inside the red sandbox around each `attack` call; the model is the constant-latency stub.

| Padding | Held-out accuracy (permutation p): exec 1 | exec 2 | exec 3 | Pooled, n=600 (95% CI) | Fit on two executions, scored on the third | Median added to answered requests |
|---|---|---|---|---|---|---|
| none | 0.795 (0.001) | 0.795 (0.001) | 0.800 (0.001) | 0.797 (0.763–0.827) | 0.797 | 0 |
| 100 ms | 0.510 (0.43) | 0.515 (0.39) | 0.545 (0.21) | 0.523 (0.483–0.563) | 0.507 | +50 to +51 ms |
| 250 ms | 0.530 (0.30) | 0.555 (0.14) | 0.495 (0.54) | 0.527 (0.487–0.566) | 0.508 | +198 to +201 ms |
| 500 ms | 0.510 (0.40) | 0.510 (0.45) | 0.495 (0.56) | 0.505 (0.465–0.545) | 0.477 | +448 to +450 ms |

Reading. Without padding the verdict leaks: 0.795–0.800, p=0.001 in every execution. With padding, the three executions give 100 ms 0.510–0.545, 250 ms 0.495–0.555, 500 ms 0.495–0.510, and none of the nine padded tests is significant (smallest permutation p 0.136; Bonferroni threshold 0.0056). Under the rule fixed before the results were inspected, every padded setting is **"no leak detected (inconclusive as to absence)"**. **The reduction is conclusive, the absence of leakage is not:** the fall from about 0.80 to about 0.5 is far outside the confidence intervals for this classifier, stub and payload set, but with n=200 per execution an accuracy up to about 0.57 cannot be told from chance (pooled 250 ms: 0.527 (95% CI 0.487–0.566, n=600)), and only one weak single-threshold classifier was tried. The right-hand accuracy column is a stricter test (threshold learned on other executions): 0.48–0.51 for all padded settings. The price is real: at 250 ms an answered request waits +198 to +201 ms longer and a 10-attack run takes about 3.9–4.4 s instead of 1.8–2.2 s.

**Broker mailbox round trip under CPU contention.** Round trip = wall-clock time of one `stats` request to the model worker through the file mailbox (polled at about 2 ms, so values are quantised). Conditions: *idle* = no CPU-hog neighbour (the desktop session and the harness itself still ran; host CPU busy 10–47%), *limited* = a neighbour with the red sandbox limits (1 CPU, 8 busy processes), *unrestricted* = a 16-process neighbour with no limit (host CPU 99.9–100%). Per execution and condition: 10 blocks of 100 timed calls (after 20 discarded warm-up calls), block order shuffled within each repetition, neighbour verified running before and after each block, so n=1000 per condition per execution. Percentage increase = 100 × (median under contention − median idle) / median idle, from the pooled samples of the same execution; the same formula is applied to p99; intervals are a bootstrap over blocks.

| Condition | Median (3 executions) | p99 | Median increase against idle |
|---|---|---|---|
| idle | 2.59–2.84 ms | 4.66–5.10 ms | n/a |
| neighbour limited to 1 CPU | 2.53–2.88 ms | 4.61–5.15 ms | -4.2% to +2.3% (every interval includes 0: no measurable effect) |
| unrestricted 16-process neighbour | 3.63–4.16 ms | 6.75–8.18 ms | +37.5% to +51.7% (intervals exclude 0 in all three); p99 +44.8% to +62.8% |

Limits: block medians vary by about 1 ms even when idle (2.43–3.45 ms) and under the unrestricted neighbour they range 2.47–4.61 ms, so the two distributions overlap and the effect is a shift, not a separation; p99 rests on the 10 slowest of 1000 calls and the slowest single call was 33.8 ms; one host, one desktop session, no cpuset pinning (controller not delegated). Cache and memory-bandwidth contention were not measured. Variable real-model latency crossing bucket boundaries was not measured.
